## Partner decisions and design

The homepage leads with supported adult learning and program oversight. One primary action opens the pilot inquiry section; Learner sign in remains a separate destination. Editorial sections explain enrollment → learning → incentive review → oversight, then the learner interaction, staff workflow, curriculum, accountability, proposed pilot process and FAQ. Warm off-white, deep ink, teal and small amber details use the established semantic tokens, Inter/system sans, rounded controls and existing Button/Dialog/Alert primitives. Marketing CSS is scoped to the marketing shell; no second styling system, decorative gradient wall or new animation dependency was added.

The product evidence is the interaction itself: `AppDemo` adapts three fictional teaching/question/optional-reflection cards through the **same CardRenderers and card adapters as LessonPlayer**. It has wrong-answer explanation, keyboard selection, local completion and retry. It does not call progress/reward/account endpoints, persist reflections or claim money. Its optional heading level preserves the real lesson's default h1. `AdminDemo` reuses the staff DataTable with three explicitly illustrative tasks, no participant API and no simulated actions. `/demo` renders the same sample component. Neither preview grants access to private records.

`lib/marketing/catalog.ts` queries only active Path → active Module → active Lesson with cards, in one repeatable-read transaction. It returns bounded public title/description/count data, never participant joins. If storage/client is unavailable, the page states this and labels three seed-authored examples; no invented published totals. Counts are not impact measures or clinical validation. Authored curriculum is unchanged.

Unsupported nonprofit/history/team, city-partnership, revenue/outcome, funding/regulatory compatibility, pricing and absolute AI/privacy claims were removed. No logo, testimonial or certification was invented. Legal pages are factual operational summaries with explicit qualified-review requirements, not approved legal terms. Human help stays available independently of the optional AI policy/provider gate.

## Inquiry operations and privacy

Intake defaults off. To enable, set all four **private names**: `PARTNER_INQUIRY_PROGRAM_ID`, `PARTNER_INQUIRY_TEAM_NAME`, `PARTNER_INQUIRY_MONITORING_NOTICE`, `PARTNER_INQUIRY_REVIEW_REFERENCE`, plus the existing private `SESSION_SECRET`. Names alone do not approve operations. Operators must verify the destination organization/program is active, at least one active MFA-enrolled program administrator can read the queue, actual monitoring/retention/deletion procedures and privacy wording are approved, and ingress/logging controls are reviewed. Store the review reference in a controlled operational record; never fabricate approval. No email/calendar provider is introduced and no delivery or response time is promised.

Minimal required fields are contact name, organization, email, interest and consent; region/message are optional. No sensitive participant information should be submitted. Recipient and actual configured monitoring notice appear before consent. The POST checks same origin, strict fields and 8 KiB body/5-second read bound before persistence; messages are limited to 1,000 characters. Storage errors never claim success. Only a server receipt confirms saved state, explicitly `notificationSent: false`, `bookingCreated: false`. This does not constitute staff acknowledgment.

A client UUID supports retries; only this key is retained in sessionStorage, never contact/message fields. The server HMACs normalized intent, serializes low-volume intake with a dedicated PostgreSQL advisory transaction lock, enforces unique receipt identity, and commits rate counters, inquiry and mandatory audit together. Conflicting same-key payloads get 409. Definitive validation errors allow editing. After uncertain failure, retry original details; a reload requires re-entering those details. Requests do not create accounts or program memberships.

Persisted limits are five new inquiries per HMAC IP per fixed UTC hour and 100 per configured intake program/hour. Exact replay returns its saved receipt without consuming another slot. Counter records store no raw IP, email or message; audit details contain no message/contact. The deployment must provide trustworthy ingress IP headers; spoofable headers weaken per-IP limiting, while the global program cap still applies. This is a low-volume limit, not a DDoS guarantee. Infrastructure logs and retention are not verified here. There is no automated retention/deletion job; approve a real retention/access/deletion procedure before enabling intake.

The staff queue is private, program scoped, read-only, paged and restricted to the authorized program-admin role. Finance/caseworker roles cannot read it; no global cross-program intake or export is provided. Contacting a prospect is a human workflow, not an automatic outbound action. Rotating SESSION_SECRET changes intent/IP hashes: resolve uncertain old receipts with authorized staff rather than blindly resubmitting under a new key. The form's saved receipt/reference can be matched to the queue. No outreach was sent during implementation.

## URL and indexing contract

`NEXT_PUBLIC_SITE_URL` must be an explicit HTTPS origin without credentials/path/query/hash/port. If `ROOT_DOMAIN` is also set it must match that validated bare domain. `ROOT_DOMAIN` alone derives its HTTPS apex origin. If missing, invalid or conflicting, canonical/indexing claims are withheld and robots disallows crawling. Do not use an unrelated guessed domain. Validate ownership and actual apex/app/admin routing before rollout. The same validation is used by middleware and Next allowed origins. `/demo`, legal and social-image routes resolve on the public apex; existing city access gates remain. Sitemap lists `/`, `/demo`, `/privacy`, `/terms` only. Gated city decks, staff, learner and API routes are excluded; city metadata is noindex. Structured data claims only a WebSite, with no legal entity/history/rating assertions.

Revert the presentation/API change with those tables retained; do not drop collected inquiry data or restore misleading claims/ungated decks. An older Prisma client can ignore additive tables, but broad legacy reset/deletion tools must be reviewed for new foreign keys. Never roll back earlier membership, financial or support safeguards. Domain configuration changes are separate operator actions.
