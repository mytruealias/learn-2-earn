# Hubert and human help

Source baseline `4e979ba`, implemented on `feat/program-boundaries` after the program/staff changes. [Audit](audit.md), [draft response policy](response-policy.md), [source verification attempts](source-verification.json), [verification](verification.md).

## Behavior and boundaries

`/lifeline` renders national human-help contacts in server HTML, without a database, account, model or completed lesson. HelpButton puts these contacts first. The catalog explicitly labels U.S. coverage and offers an outside-U.S. explanation; it does not infer physical location from city/profile data. Removed unverified local contacts, the mislabelled SAMHSA number and absolute confidentiality/free-service claims. No app emergency dispatch, continuous monitoring or automatic escalation exists.

Hubert uses the existing original `HubertIcon`, restrained purple and shared CSS tokens/native dialog. It explains that it is an optional AI support tool, can be wrong, is not a clinician, cannot access cases/rewards, and cannot contact people. Human links remain visible independently of model output. Model text is rendered as plain text with no executable links/actions. This does not establish exhaustive response safety or prevent all prompt injection; there are no private-data tools to authorize.

AI chat and cloud voice are disabled unless a private `OPENAI_API_KEY`, exact `HUBERT_APPROVED_POLICY_VERSION=hubert-2026-10-31-v1` and nonempty `HUBERT_REVIEW_REFERENCE` are all configured. **These values represent an external review record; setting an environment variable is not clinical review. No qualified human review occurred here. Do not enable AI until the review and privacy/resource gates below are complete.** A model/policy change requires another recorded review and version change. Device voice is opt-in and uses only a voice marked local by the browser; cloud voice requires a separate choice and has no automatic fallback. Device dictation has its own provider behavior.

## Processing, limits and privacy

`lib/support/bounded-json.ts` enforces JSON content type, declared and streamed bytes, a five-second read deadline and request cancellation before database/provider work. Chat accepts only strict user/assistant objects, 1–12 messages, 1,000 characters per user message, 4,000 per supplied assistant message, 12,000 total characters and 49,152 bytes. A final user message, explicit processing choice and matching server-session account context are required. Supplied assistant text is untrusted history, never authority. No client system/developer/tool role, tool definition, provider URL or model selection is accepted.

OpenAI SDK logging/retries are off, timeout 20 seconds, chat request lifetime 30 seconds, output 500 tokens/6,000 characters. `store:false` is sent on chat. No record lookup/actions/tools are attached. Client stop/close/disconnect cancels upstream and releases its lease; partial/interrupted responses are labelled incomplete, never falsely DONE. UI stops a stalled reply after 35 seconds. TTS accepts 2,000 characters/12,288 bytes, has a 20-second lifetime and 4 MiB response ceiling. No automatic retries consume more provider usage.

PostgreSQL serializes metadata-only usage per active learner: one in-flight chat and one in-flight TTS lease (60-second expiry); 30 chats/120,000 input characters per fixed UTC hour; 120 voice calls/hour and `TTS_DAILY_CHAR_CAP` (default 20,000) per fixed UTC day. Failed admitted provider attempts consume usage, preventing retry storms. Human help and learning are independent of these budgets. These are per-account controls, not a claimed organization-wide spend ceiling; operators must configure provider spend limits and monitor aggregate usage without message content.

Application source stores no chat transcript in Prisma or browser storage and logs no chat/TTS bodies/provider errors. There is no analytics integration in these components. Usage contains account ID, counters/window, policy version and leases only. This is a source-level statement, **not proof of hosting/proxy/APM capture or provider zero retention**. `store:false` does not remove all provider processing/abuse retention. Actual host logs, provider contract/account retention, access, geography, subprocessors and deletion require operator verification; no values/private conversations were inspected. Privacy UI explicitly distinguishes these unknowns.

Program requests are different: the chosen message and optional location are stored as private scoped `Case` records, accessible to authorized program caseworkers/administrators (finance denied). Audit stores only case ID, location-sharing boolean and notificationSent=false, not the message/location. No AI transcript is copied into a case. Browser sessionStorage retains only an opaque request key namespaced to the account; message/location remain in component memory. A reload loses unsent text deliberately but can query the existing key’s receipt. Account-context checks reject sharing from stale tabs signed into another account.

## Program intake and staffing runbook

New program intake defaults **off**. Program administrators configure the actual responsible team, monitoring hours/timezone/absence coverage, region and external review record under `/admin/security#program-support-intake`. The confirmation explicitly says this does not enable notifications or emergency response. There is no hidden default team or promise that a queue is staffed. Settings changes are versioned, role checked and audited.

Before enabling, assign an actual caseworker rota, ownership/absence handoff, queue-check frequency and consent/privacy/retention policy. Display only the schedule that exists. Regularly inspect `/admin/cases?status=unacknowledged` and the dashboard count. Staff must explicitly record acknowledgment after reading a request; opening a page, saving a note or model output does not acknowledge it. The learner can check the server-recorded timestamp. It is not proof of notification, completed follow-up, continuous monitoring or a response-time promise. Record subsequent support activity through existing versioned case workflows. Out-of-hours/urgent needs must use human contacts directly, not await this queue.

Intake requires an active enrollment/program/organization, configured team and monitoring, review reference, resource region, UUID intent and explicit location-sharing choice. Location is optional, never geolocated; a request without location is equally valid. Account lock + unique `(userId,intakeKey)` + payload fingerprint create exactly one case/audit for unchanged retries; mismatched reuse is rejected. Six new requests/hour limits accidental repeats; checking/replaying existing requests is allowed. Sent/saved status requires a server receipt. A timeout says the outcome is unknown and offers unchanged retry/status check. There is no automatic email/text/pager/provider integration.
