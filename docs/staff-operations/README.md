## Query, conflict and export contracts

List endpoints accept bounded search, page, sort/direction and applicable status/priority/category filters, with stable ID tie-breakers and twenty-row database pages. The URL is the list state. Stale fetches abort; previous results remain visible while updating, with a status message. Empty results and failures are distinct. Program scope headers protect stale tabs and are never identity proof. Restricted browser storage falls back to a verified in-memory scope hint.

Case, service, participant and membership writes carry an expected version and UUID intent. Stale simultaneous writes refuse with a reload/review instruction. Successful intents have a durable receipt; repeats do not apply another mutation. Notes, allocations, versions and mandatory audit commit together. Staff cannot edit another program through a guessed ID. Money state/reservations remain governed by the prior ledger; no payout economics changed. External references and pool intent uniqueness are program-local so independent organizations do not share a bookkeeping namespace.

No bulk mutation is added. Filtered list CSV discloses program/match scope and exports up to 5,000 rows; larger requests must be narrowed. CSV quotes all fields and neutralizes formula prefixes after whitespace/control characters. Default list exports exclude emails, participant phones, messages, locations, private notes/reflections and payment handles; service-directory export includes the actual service contact fields. Staff/audit exports require program administrator. Report CSV contains aggregates/definitions/filter metadata only. Exports are server-authorized and audited.

## Metric definitions and boundaries

- Participation denominator: currently active program enrollments, including inactive sign-in accounts; this is not a reconstruction of enrollment at the beginning of a historical window.
- Participating accounts: distinct enrolled accounts with a first completion or completed practice in the selected local dates.
- First completions: unique Progress records; practice sessions: separately persisted completed practice attempts, with no duplicate monetary credit.
- Service activity: recorded allocations/counts/quantities, not verified receipt or self-reported outcomes. Support cases created are a separate count.
- Paid incentives: completed requests by actual paidAt and exact cents; approvals are excluded. Undated legacy completions are disclosed separately and excluded from dated windows. Unknown exact values require reconciliation, not a zero.
- No self-reported housing/recovery outcome collection or causal impact estimate is invented.

Report ranges are inclusive local calendar dates (maximum 366 days); database boundaries are an explicit UTC instant and exclusive end after the final local date. PostgreSQL timezone conversion handles daylight-saving changes. Program scope comes from authorized session selection; changing a filter cannot select another program without a membership and deliberate switch. A report reflects the records available when calculated/exported, and is not a verified bank statement.

## Release and rollback

Requires the program-boundary migration and additive staff-workflow migration (`20261029000000_staff_workflows`: optimistic versions, follow-up/resolution timestamps, durable action receipts and query indexes). Existing completed cases do not acquire guessed historical resolution dates. No account, XP, curriculum identifier, balance or paid-history reset occurs. New runtime MFA key and deliberate legacy mapping are described in [program release guidance](../program-boundaries/README.md). Existing Replit binding stays 0.0.0.0:5000; live configuration, production baseline/backup/restore/mapping, manual credential handoff and remote CI remain unverified.

Rollback presentation with compatible scoped authentication/accounting/workflow APIs and keep additive evidence/schema. Disable private writers during an incompatible rollback; do not restore global authorization, nontransactional financial checks, silent seeds/history repair or old cookie-only logout. Reconcile subsequent activity and real payments before any reviewed backup restore.
