# Learner access and continuity

Implemented on `feat/learner-access-journey`, based on design-system commit `8e34d84`. This stage keeps the existing App Router, React, TypeScript, Prisma/PostgreSQL and CSS Modules. No production database, provider, deployment or payout-rule operation is part of validation.

## Journey and navigation

1. `/access` accepts the existing program invitation code, then offers account creation, existing-account sign-in or explicit guest exploration. Rejected/unconfigured access explains the next supported action. Existing account holders can sign in without entering the program code again.
2. `/signup` asks only for the name a person uses, email and password. The server derives guest ownership from the cookie. Birth date, phone, address, case identifiers, emergency contacts and payment details are deferred. Browser drafts do not store these fields or passwords.
3. `/onboarding` gives two brief steps: program/learning/incentive expectations, then privacy and an optional goal. Goals are fixed non-sensitive reminders; there is no deadline or reward condition. New accounts are marked pending until completion; the same account resumes after reload. Existing accounts are not forced into onboarding. Completing the step is idempotent.
4. `/app` shows real server-derived progress, earned XP, the next active lesson and available paths. It does not invent a streak, balance or heart requirement. Read failures remain errors with recovery, not zero-valued progress.
5. Learn, Rewards, Profile and Help have actual destinations. Rewards opens the existing profile earnings view; eligibility links to the existing request section. There is no standalone Practice route, so no dead Practice tab is added; completed lessons remain available for review. Help `/lifeline` is available without an invitation or account; authenticated support submissions still require a session.

The shell uses the shared design tokens and Inter with a compact mobile bar and a desktop sidebar at 64rem. The active destination is labelled with `aria-current`; safe-area insets and measured navigation height reserve content space. When a focused form and VisualViewport resize indicate an open keyboard, the bar returns to document flow and header Help remains reachable. Root-text enlargement reflows the compact bar into two columns. The existing lesson interface remains immersive, with a persistent Help destination and visible session/save recovery.

Forms explain disabled/pending actions, validate and name errors, focus the first invalid field, show a slow-network message and retain entered values on failure. Server-rendered controls wait for hydration so an early click cannot be lost before handlers attach. A timed-out signup is explicitly uncertain: sign in with the same credentials before repeating it. A successfully created account resumes onboarding, and email uniqueness prevents a second account for the same address. No promise is made about recovery when the user chooses a different email.

## Identity boundary

- **B17 is closed in source and regression tests:** `/api/user/ensure` accepts an empty object only, requires program access for a new guest and generates its ID on the server. A supplied account/guest ID never mints that identity. With an existing valid cookie it resumes the same record; an expired/revoked cookie is not silently replaced by a new guest.
- Registration accepts minimal credentials, never arbitrary `guestId`/`userId`. It locks the proven guest, upgrades that same `User` row and preserves identifiers, XP, progress, existing personal details, consent and payout history. Session rotation and an audit record are committed in the transaction. Competing registrations cannot overwrite the first account's credentials. Signing into a separate existing account does not merge financial/progress histories; the UI explains that the guest session ends.
- New `LearnerSession` rows store a SHA-256 digest of a random, HMAC-signed cookie, not the replayable token. Middleware verifies signature and age; server pages and all existing learner API consumers additionally check database expiry/revocation and active account state. The 30-day lifetime is enforced on both sides.
- **B20 is closed:** malformed, old/future and expired tokens are rejected. Logout revokes the current database session before clearing cookies, preserves other devices and flushes the private client view by full navigation. A failed logout does not claim success. An expired shared-device session can be deliberately cleared through an explained confirmation; a new guest then receives a separate server ID while the old record/history remain intact.
- `SESSION_SECRET` is mandatory for learner/demo signing. A shared invitation code or fallback string is no longer a signing key. Keep the reviewed existing private secret stable during rollout; do not silently rotate it and abandon legitimate guest access.
- Valid old signed **guest** cookies are admitted only while still guests, within their original 30-day age, with a lazily created revocable session row. Legacy registered cookies require password sign-in because the previous unauthenticated bootstrap could mint those cookies. No balances or history are removed. Lost/expired unsigned localStorage IDs cannot safely prove ownership; staff-assisted review is required rather than an insecure ID-recovery endpoint.
- Auth/bootstrap mutations check the browser Origin against the incoming Host/proxy protocol. Non-browser callers still need credentials/invitation. Redirect destinations use a small route allowlist; absolute, protocol-relative, encoded and control-character destinations fall back to `/app`.
- Learner identity flags are no longer read from localStorage anywhere. Only legacy cleanup and existing non-identity Hubert preferences remain. Navigation reads only an ID and guest/account kind from the minimal no-store session description; no name/contact/payout data is included. Public marketing previews do not request or embed live learner identity. Private pages carry no-store/noindex headers and recheck restored/focused sessions.

The in-memory rate limiters remain single-instance controls, not a distributed abuse guarantee. Existing lesson bonus authority, completion/XP atomicity, payout races, hard-coded badge claims, Zelle mismatch, staff logout revocation and missing partner boundaries are separate baseline tasks. This stage does not certify the full legacy profile, lesson or support UI as WCAG compliant.

## Account recovery

No email/SMS delivery provider or learner password-reset mechanism exists in the checkout. `/recover` therefore collects no recovery address, sends nothing and says so. It directs the learner to the program staff who invited them, through an already trusted contact, for identity-verified escalation to the operator. It does not assert that the current staff UI can reset passwords or that a message was delivered. Support must not use a submitted user ID, payment destination or unverified email as ownership proof.

A future automated recovery feature needs an operationally verified delivery channel, expiring single-use hashed tokens, rate limits, non-enumerating responses, session invalidation and delivery/reset integration tests. No unverified mail address or simulated reset is substituted here.

## Migration, release and rollback

Required additive migration: `prisma/migrations/20261027000000_learner_sessions_onboarding/migration.sql`. It adds nullable `User.onboardingState` / `User.learningGoal` and the indexed `LearnerSession` table. Existing accounts remain with null onboarding fields. No user/progress/payout/curriculum backfill, reset, seed or reward conversion is needed. Legacy guest session rows are created only after signed proof and expire on the original schedule.

Before any separately authorized release, follow [DEPLOYMENT.md](../../DEPLOYMENT.md): verify the existing migration baseline and database target, test backup restoration, apply the additive migration before starting the new artifact, and verify runtime `SESSION_SECRET`. Builds still do not migrate or seed. The historical missing-init migration issue is not repaired by this migration. Actual Replit settings remain unverified; binding stays 0.0.0.0:5000. No new recovery/provider environment variable is introduced.

Retain the additive table/columns on rollback. UI changes can be reverted independently while retaining the corrected server identity boundary and compatible minimal request bodies. Do not deploy the old arbitrary-ID bootstrap/merge or return to accepting unsigned age-unchecked identity. Use a forward fix or disable signup/bootstrap while correcting a server regression. Existing registered sessions may need to sign in again; guest association must retain the same row/history. Expired session cleanup, if needed operationally, must be a separate reviewed job; no cleanup/reset is hidden in build or ordinary release.

## Verification and evidence

The dedicated harness creates a fresh PostgreSQL database and restricted role for each suite and requires a server capability/ownership proof before resets/fixtures. Suites run sequentially. [Screenshot index](screenshots/README.md) and [stage status](../upgrade-status.md) record final executed checks and limitations. `npm run test:journey` is included in `npm test` and therefore existing GitHub CI.

Automated checks exercise server ownership, concurrent/repeated signup, expiry/revocation, disabled accounts, migration preservation, redirect policy, real UI flows, field semantics, keyboard focus, axe, 44px targets and text reflow. Browser evidence uses only synthetic people, resources and curriculum. Actual screen-reader speech, native mobile keyboards, physical-device safe areas, browser-menu zoom, live delivery and production Replit behavior require separate manual/infrastructure verification; no certification or deployed result is implied.
